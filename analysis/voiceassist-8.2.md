## 新设备运行证据

- 通过 USB 连接的 `2304FPN6DC` 设备实际加载新版本的 LSPosed 映射。使用局域本机测试服务核对对话请求；Hook 报告 `自定义请求成功：chat / FIXTURE_CHAT`。
- 语音通道以测试文字作为输入，经兼容聊天接口后触发原厂播放；收到 `原厂 TTS 播放结束（中断=false）`。这次未仿造 ASR 末段结果，也未重新验证真麦克风采集。
- 绘图请求走兼容图片接口，返回的真实测试位图在小爱原生绘图卡片可见。UIAutomator 因窗口持续刷新未取到绘图 XML，结论来自实际请求与像素检查。
- 在模块设置页记录点按前后帧；返回手势中途可见上一页预览，取消后恢复到原子页，完成后回到首页。未改系统的手势导航配置。
- 自定义控制仅做了本地测试。原厂能力在 `Application.attach` 时尚未就绪，收到实际请求后才返回支持。经双重授权的测试收到 7 次模型调用及截图摘要，但操作提交后测试页计数、输入与滚动都没有变化，未通过实际操控验收。新版继续使用原厂控制，未启用实验执行路径。
- 后续定位确认系统拒绝把首次点击交给授权的测试页：触点判给了 `NotificationShade`。具体窗口交接对照见下文。

## 双工语音接管

普通语音发 `SpeechRecognizer.Recognize`，双工语音由 `p31.o0.U0` 发
`SpeechRecognizer.DuplexRecognizeStarted`，两路都进入已匹配的 `p31.o0.D0`。
双工的外层事件 ID 由 `a41.g` 管理，识别回包使用独立的每轮 ID。真机基线中，
同一外层 ID 对应两个非空 ASR 末段及两轮原厂回答；旧模块只识别普通入口。

现在双工事件也保留原厂 ASR、禁用该请求的原厂 NLP / TTS；按同一引擎实例和原厂
当前事件 ID 关联识别轮次。只把非空末段提交给自定义模型，同一轮不重复提交，
不拦截无关会话。响应仍回填原生卡片、调用原厂 TTS。7.11 的普通语音行为不变。

用户在同一浮窗连续提出两道算术题，确认两句都正常播报；真机记录显示请求进入
`voice / gpt-6.2-sol`，并完成原厂 TTS。测试不改 Provider 配置。

## 手机控制：输入命中与原厂窗口交接

三次测试使用自有测试页报告的默认屏幕尺寸 `1440×3200` 和按钮边界
`[32,294][1408,454]`，首个点击取中心约 `(720,374)`。模型记录里的 `576×1280`
是同一纵横比的缩略截图，触摸仍按实际显示尺寸换算。设备确认小爱进程具有输入权限，
双重授权检查也没有阻断请求；每次都收到第一轮本机模型请求，但没有后续工具结果。
`InputDispatcher` 在三次测试分别于本机时间 03:36:15、03:39:39、03:40:39 报告：
目标为测试页 UID 的点击实际会交给 SystemUI 的 `NotificationShade`。同步目标校验
因此拒绝投递；测试页没有收到 `ACTION_DOWN`，计数、文本和滚动均未变化。
两轮间曾观测到通知区域不在屏幕上；最后一轮仅关闭模块自有 PAG 光效，仍复现相同命中。
这是输入路由拒绝，而非已确认的坐标换算、模型调用、授权或单独的 PAG 故障。

原厂前台 Plan B 在 `com.xiaomi.voiceassist.baselibrary.uiagent.e` 的
`onStartExecute → J` 先处理锁屏，随后通过 `hideFloatView` 切换原厂浮窗状态，
为会话设置实际屏幕矩形并交给原厂窗口管理器；它还随 `userTouchScreenFlow`
更新 `UIAgentTakeoverBar` 的触摸标志，在 `onExecuteEnded` 解绑监听、释放窗口。
其中 `com.xiaomi.voiceassistant.s.hideFloatView` 是管理器状态迁移，不是把
当前进程的 View 调透明。此前实验仅调整当前进程拥有的窗口属性，未观测到系统侧完成
相同的焦点与触摸交接。原厂截图工具 `r21.t` 还会过滤状态栏、导航栏和原厂控制遮罩等
层；截图内容和顶层任务都不能单独证明某坐标的实际接收窗。

原厂输入 helper `h0.injectEventIntoDisplay` 的末参控制事件回收，
两条分支都使用异步投递；其 `true` 不是触摸到达测试页的证据。原厂另外有
输入诊断结果，带结果码和目标 UID。后续测试使用了
[AOSP 的同步目标 UID 接口](https://android.googlesource.com/platform/frameworks/base/+/b69dbff6d1ec93e6e450a7fe01e3175c91ab3806/core/java/android/hardware/input/InputManager.java#1016)
来确认接收对象并在不匹配时停止，没有改用不限目标的输入方式。

目前缺少的是**首个触点发生当时**的输入窗顺序、触摸区域及焦点，尚不能确定
`NotificationShade` 为什么参与命中。下一轮可在用户配合下，对同一自有测试页分别
观测正常原厂 Plan B 和模块路径：在唤醒前、浮窗退场后、首个动作前记录默认显示旋转、
目标任务、焦点和命中窗区域，仅保留这些元数据。另可在测试包里对照正常唤醒与显式启动
`FloatActivity` 的差异，以区分测试预热和真实窗口交接。验收仍以测试页实际收到触摸、
输入及滚动，以及本模块任务独立停止为准；不修改系统权限、不放宽目标 UID、不调用原厂全局停止来证明模块任务停止。
